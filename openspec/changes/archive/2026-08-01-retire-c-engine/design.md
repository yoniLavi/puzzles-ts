# Design — retire-c-engine

## Context

The migration is functionally complete: every catalogued game runs on the TS
engine (`src/native/engine/` + `src/native/games/`), and the runtime never
enters the C/WASM path. What remains is *removing* the C engine and its scaffold
— a large but mechanical teardown whose only real risk is that two things the
app still needs are currently produced by the very build being removed.

This is deliberately its own change (not folded into any game port) because it
is architectural: the decisions below are about build topology and the worker,
not about any game.

## D0 — The app's type vocabulary is generated by the toolchain being deleted (do this first)

Found by reviewing the change against the build, 2026-08-01. It is the one thing
here that stops `tsc` dead, and the original draft did not mention it.

`src/puzzle/types.ts` does not merely *use* the Emscripten output — it
**re-exports fourteen types straight out of the generated
`src/assets/puzzles/emcc-runtime.d.ts`**: `Colour`, `Point`, `Size`, `Rect`,
`KeyLabel`, `PresetMenuEntry`, `DrawTextOptions`, `NotifyGameIdChange`,
`NotifyGameStateChange`, `NotifyParamsChange`, `Frontend`, `Drawing`,
`DrawingWrapper`, `FrontendConstructorArgs`. `ConfigDescription`, `ConfigItem`
and `ConfigValues` are then derived as `ReturnType<Frontend[…]>`.

**202 files import from `puzzle/types.ts`** — the whole TS engine, all 57 game
ports, the render-scenario harness, the colour palette. So the native TypeScript
engine's type vocabulary is, today, emitted by `emcc --emit-tsd` from
`webapp.cpp`. Nothing flagged it because `tsc` was only ever run on a tree where
`build:wasm` had already populated `src/assets/puzzles/`.

**The general shape worth remembering: at the end of a migration the dependency
inverts.** The replacement was built to fit the thing it replaces, so an artefact
everyone treats as a leaf — a generated `.d.ts` in a gitignored assets directory
— turns out to be the root of the type graph.

**The fix is contained**, which is why this stays one change: hand-author the
declarations *in `types.ts` itself*, preserving each shape exactly, and every one
of the 202 importers changes by zero characters. Only two other files touch the
embind-specific types at all:

- `src/puzzle/drawing.ts` — loses `bind(module)`, and `DrawingImpl` must be
  restated directly instead of as `Omit<DrawingWrapper, keyof ClassHandle | …>`.
- `src/puzzle/worker.ts` — loses the whole `Frontend`/`PuzzleModule` surface with
  `WorkerPuzzle` (D4).

`Frontend`, `PuzzleModule`, `ClassHandle`, `DrawingWrapper` and `MainModule` are
referenced *nowhere else in `src/`*, so they retire with `WorkerPuzzle` rather
than needing hand-authored replacements.

**The check that the transcription was faithful is "no importer needed to
change".** If a downstream file wants an edit, a shape drifted — fix the shape,
not the importer.

## D1 — What is genuinely orphaned, verified against the build (not assumed)

After Loopy, `add-loopy-ts-port` already dropped the Loopy grid subtree
(grid/loopgen/penrose/hat/spectre) but **kept `tree234.c` on purpose**, because
`latin.c` still uses it and `latin.c` was out of that change's scope. Both are
now runtime-dead and retire here, together.

Do not delete from a remembered list — **re-derive the orphan set against the
current build** (`grep` includers, check the `core_obj`/`common` source lists,
build after each removal). The expected set: `tree234.c`, `latin.c`, `combi.c`,
`dsf.c`, `findloop.c`, `sort.c`, `midend.c`, `drawing.c`, `misc.c`, `malloc.c`,
`tdq.c`, `ps.c`, `draw-poly.c`, `version.c`, the random stack, the null
frontends, and `webapp.cpp`. Two traps:

- **`matching.c` is both a core source and an auxiliary program** — check both
  roles before removing it.
- **`divvy.c` is already gone** (deleted when Separate shipped, 2026-07-04). The
  old "separate blocker" note is stale; verify, don't re-introduce it.

## D2 — Catalog and manual generation must outlive the Emscripten build (the real risk)

`scripts/build-emcc.sh` copies `catalog.json` out of the cmake build and runs
halibut over `puzzles.but` to produce the in-app manual HTML. The app depends on
**both**, and both currently ride on the toolchain being removed. So the
teardown is not pure deletion:

- **`catalog.json`** — today unioned from the wasm-built games plus the
  `ts_ported_names` list. With no wasm games it is *entirely* the TS list.

  **Corrected 2026-08-01 — the first draft of this bullet was wrong.** It said
  the catalog "can be generated directly from the TS catalog metadata (the same
  data `ts-ported-ids.ts` and the per-game registrations already hold)". It
  cannot: `ts-ported-ids.ts` is a bare `Set<string>` of ids, and the `Game`
  interface carries no display metadata at all. Every game's `name`,
  `description`, `objective` and `collection` exists **only** in the `puzzle()`
  macro calls in `puzzles/CMakeLists.txt` and
  `puzzles/unreleased/CMakeLists.txt` — inside the tree being deleted.

  So this is a **data migration**: transcribe all 57 games' metadata into a
  committed TypeScript source of truth (`src/puzzle/catalog-data.ts`), and have
  the catalog fall out of it. Verify by **deep-equality against the current
  `catalog.json`** (built at `5cf34c1`) for all 57 entries, not by eyeballing.

  Two things to fix while there, both real warts the cmake route left behind:
  - `catalog.json.version` came from cmake's `VCSID`; vite already computes the
    git SHA, so the version comes from there.
  - `vite.config.ts` **imports `./src/assets/puzzles/catalog.json` at config-load
    time — from a gitignored directory.** A clean checkout today cannot even
    parse the vite config without first running the wasm build. Making the
    catalog a committed source removes that bootstrap dependency entirely.
- **The manual** — halibut over `puzzles.but` is independent of Emscripten
  (halibut is its own brew tool). Keep the halibut invocation, drop only the
  wasm compilation around it. `puzzles.but` and `/puzzles/html` stay.

**Sequence the removal so these two are re-homed first**, then remove the
Emscripten build. Verify by building the app and loading a game + the help pages
with no `build:wasm` having run.

## D3 — Decide the Web Worker's fate

The worker exists because WASM was heavy and blocked the main thread. Pure-TS
games may not need it. Options:

- **Keep it** — lowest-risk; the Comlink surface and `TsWorkerPuzzle` already
  run there, and heavy generators (Loopy Hard, Solo) still benefit from being
  off the main thread. **Recommended for this change**: retiring the C engine
  and moving the game off-thread are separable concerns, and doing both at once
  widens the blast radius.
- **Remove it** — simplifies the app but must prove no generator janks the main
  thread. Defer to a follow-up if wanted.

Record the choice; default to keeping the worker so this change stays a *removal
of dead C*, not a threading rearchitecture.

## D4 — The worker dispatch collapses to one implementation

`src/puzzle/worker.ts` currently constructs either `WorkerPuzzle` (C/WASM, line
107) or the TS engine via `createTsEngine` (line 506), behind the shared
`PuzzleEngineSurface`. With no C games, `WorkerPuzzle`, `assertWasmBridgesCoherent`
and the WASM-instantiation path are all dead. The seam collapses to always
constructing the TS engine. The **shared `PuzzleEngineSurface` interface can
stay** (it is harmless and keeps the app-facing type stable), or be inlined — a
judgement call at implementation time; keeping it is lower-risk.

## D5 — `puzzles/` survives this change as a docs tree (owner decision, 2026-08-01)

The proposal's original claim that only `LICENCE` would remain is not achievable
as scoped, because two things under `puzzles/` are **served to players** and have
no C dependency:

- `puzzles/puzzles.but` → halibut → the in-app manual at `/help/manual/*`.
- `puzzles/html/**/*.html` → 43 per-puzzle overview pages at `/help/<id>.html`
  (`vite.config.ts`, the `sources: "puzzles/html/**/*.html"` entry).

That collides with the `repo-layout` requirement `audit-author-known-issues`
added — player-facing help pages "SHALL NOT live inside `puzzles/`" — which is
exactly why the thirteen unreleased pages moved to `help/games/`. These 43 plus
the manual source are the same kind of artefact and did not move.

**Owner's call: relocate them, but as a follow-up change** —
`rehome-upstream-help-sources`. This change therefore leaves `puzzles/` holding
`LICENCE`, `puzzles.but`, `html/`, and the two unbuilt `unfinished/` references,
and the `ts-migration` delta says so rather than promising `LICENCE` alone. The
contradiction with the repo-layout requirement stays visible in the specs until
that follow-up lands, which is the honest state.

One thing that *does* move here, because it documents live TypeScript rather
than deleted C: `puzzles/auxiliary/doc/*.svg`, the hat/spectre tiling diagrams
that explain `src/native/engine/tilings/`. They go to `docs/`, not to the bin.

## D6 — The "TS" engine badges retire with the migration (owner decision, 2026-08-01)

`catalog-card.ts` renders a green "TS" chip and `puzzle-screen.ts` an in-game
`TS`/`C` badge, both fed by `PuzzleStaticAttributes.engineType`. They existed so
an owner doing parity testing could see which engine a game was on. With every
game TS-served the chip appears on all 57 cards and marks no distinction — it
advertises a migration that is over. Remove both, and the `engineType` /
`PuzzleEngineType` field behind them.

## Risks

- **Build wiring (D2)** is the whole risk. A missed catalog/manual dependency
  makes the app un-buildable or help-less. Mitigate by re-homing generation
  first and building the app with no wasm present before deleting the toolchain.
- **Over-deletion (D1)** — deleting a `.c` a remaining unit still links breaks
  the (now much smaller) build; re-derive the orphan set, build incrementally.
- **Scope creep (D3)** — folding a worker-removal or a threading change in here
  widens a mechanical teardown into a rearchitecture. Keep them separate.
