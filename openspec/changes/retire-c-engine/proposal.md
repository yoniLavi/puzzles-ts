# retire-c-engine

## Why

Loopy was the last game (`add-loopy-ts-port`). Every catalogued game now runs on
the native TypeScript engine; no game is served by C/WASM. The C engine, the
Emscripten build that produced it, the worker's WASM dispatch path, and the
`USE_TS_LEAVES` leaf-bridge machinery are therefore **dead weight** — still
compiled, still maintained, consumed by nothing at runtime.

This change removes them. It was deliberately kept separate from the per-game
ports (each port's proposal says so): it is an architectural teardown, not a
game port, and it deserves its own design because the risk is entirely in the
build wiring — the catalog and the in-app manual are *currently* generated by
the same Emscripten build that compiles the (now unneeded) wasm, so that
generation has to survive the teardown.

## Sequencing (owner decision, 2026-08-01)

**This is the next change to implement.** The five changes that the released
byte-match oracle reopened — `grade-difficulty-tiers-honestly`,
`add-clusters-difficulty-tiers`, `add-subsets-difficulty-tiers`,
`add-sticks-difficulty-tiers`, `add-latin-repeats-support` — plus
`bound-abcd-generable-sizes` and `refine-slide-appearance` all wait until the
codebase is TypeScript-only, and possibly until a round or two of refactoring
after that, so that work lands on cleaner code.

Two consequences of that order, both fine, both worth knowing:

- **The 48 per-game differentials survive this change and must not be deleted.**
  Each imports a *frozen JSON fixture*; the C build appears only in a comment
  explaining how the fixture was produced. They keep working with no C present,
  and they are exactly the regression net a refactoring round needs — a refactor
  that changes a solver's verdict changes which boards exist, and these are what
  catch it. Only the *regeneration* path dies here (`scripts/build-native.sh` and
  the `puzzles/auxiliary/*-trace.c` harnesses).
- **After this, a divergence is one-way.** With no C build there is no answering
  "what would upstream have produced?" for a new question, and a fixture cannot
  be re-baselined against C. That is the intended consequence of releasing the
  oracle — a deliberate divergence retires or re-founds its fixture rather than
  re-recording it — and `puzzles/` remains in git history if a question ever
  genuinely needs it.

## Depends on

- **`audit-author-known-issues`** — **landed.** The authors' own known-issue
  lists lived inside `puzzles/`, which this change deletes wholesale. They are
  now reconciled and preserved: every point and its verdict is in that change's
  archived `audit.md`, and the per-puzzle help pages that carried them have moved
  out of the subtree to `help/games/` (a `repo-layout` requirement now says they
  must not live in `puzzles/`). Note for this teardown: **`help/games/` is a
  source directory, not a build output** — the vite entry that renders it reads
  from `help/games/`, no longer from `puzzles/unreleased/docs/`.

## What Changes

- **Delete the runtime-orphaned C sources.** After Loopy the C files with no
  remaining consumer are the shared leaves and the C midend/drawing stack:
  `tree234.c` + `latin.c` (latin uses tree234; every latin-family game is
  ported), `combi.c`, `dsf.c`, `findloop.c`, `sort.c`, `midend.c`, `drawing.c`,
  `misc.c`, `malloc.c`, `tdq.c`, `ps.c`, `draw-poly.c`, `version.c`, the random
  stack, and the null frontends. Confirm each against the build before deleting;
  `matching.c` is both a core source and an auxiliary program.
- **Delete `webapp.cpp`** — the Embind adapter between the C games and the TS
  worker. With no C game it adapts nothing.
- **Remove the Emscripten build** — `scripts/build-emcc.sh`, `webapp.cmake`, the
  `build:wasm` path, and the `src/assets/puzzles/*.wasm` outputs. **Preserve the
  catalog + manual generation** that currently rides on it (see design D2).
- **Remove the worker's WASM path** — `WorkerPuzzle`, the C branch of the
  `createTsEngine` dispatch seam, `assertWasmBridgesCoherent`, and the
  `USE_TS_LEAVES` / `VITE_USE_TS_LEAVES` umbrella plus every per-module
  `USE_TS_*` flag. These exist only to gate C-internal leaf bridges that no
  longer have a C side.
- **Re-evaluate whether the Web Worker survives at all** (flagged in the
  `ts-migration` spec). It exists for heavy WASM; pure-TS games may not need a
  worker thread. Decide here (design D3).
- **Resolve the `ts-migration` requirement this change satisfies.** "Author-stated
  known issues are reconciled before the C is retired" (added by
  `audit-author-known-issues`) is a gate on *this* change, and its scenarios stop
  being testable once `puzzles/` is gone. Retire or restate it here rather than
  leaving a requirement whose trigger can never fire again — the reconciliation
  itself is preserved in that change's archived `audit.md`.

Explicitly **not** in this change:

- **`divvy.c` stays only if still coupled** — it was already deleted when
  Separate shipped (2026-07-04), so verify it is truly gone before assuming the
  historical "separate blocker" applies; it does not.
- **`puzzles/LICENCE`** stays permanently (MIT obligation).
- **The unfinished puzzles** (`puzzles/unfinished/`) and their build are out of
  scope — they are governed by the per-game `add-{group,slide,sokoban,numgame,
  path}-ts-port` changes.

## Impact

- Affected specs: `ts-migration` (the migration reaches its terminal state — C
  fully gone), `ts-engine` (only one engine surface remains; no dispatch
  branch), `build-pipeline` (the Emscripten/wasm build and the leaf-flag
  machinery are removed, replaced by a wasm-free asset build).
- Affected code: large but mechanical deletions across `puzzles/`,
  `src/puzzle/worker.ts`, `src/puzzle/` (the `WorkerPuzzle` path), `scripts/`,
  `vite-plugins/`, and the CMake tree; plus whatever now generates `catalog.json`
  and the manual.
- Risk is in the **build wiring**, not logic — do it with the app running so a
  broken asset path surfaces at once. Reversible via git if a catalog/manual
  dependency was missed.
